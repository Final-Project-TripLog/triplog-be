# ✏️ ElasticSearch 란?

- 분산형 Restful 검색 및 분 석 엔진
- JSON 기반 문서를 저장하고, 이를 빠르게 검색/분석할 수 있는 오픈소스 솔루션


- Elasticsearch는 JOIN을 지원하긴 하지만, 추천되지 않고 대부분 안 씀
대신, 필요한 데이터를 한 문서에 역정규화하여 저장

- 빠른 검색의 핵심은 역색인 구조 + 문서 중심 모델링 + 분산 시스템

# ✏️ 역정규화 데이터를 저장 방식

### MySQL에 역정규화 테이블 만들어 저장
- 이력 관리와 트랜잭션 용이
- 데이터 파이프라인 안정성 증가

### Elasticsearch에 저장
- 중복 저장 방지
- 가볍고 빠름
- 동기화 로직이 직접 관리 되어야함

# ✏️ 어차피 역정규화 테이블 만들거면 왜 Elasticseach를 사용해야하는가?
## 📌 MySQL로 충분한 경우
- 단순 CRUD + 조건 필터링
- 정형 데이터 위주 (날짜, 숫자 조건)
- 검색 결과 수가 많지 않고, 실시간성도 덜 중요
- 개발자 전원이 SQL에 익숙하고, 인프라가 단순한 게 중요

## 🚀 Elasticsearch가 필요한 경우
✅ 아래 하나라도 해당되면 Elasticsearch 도입 고려

- 검색창에 텍스트 검색 + 자동완성 + 오타 대응(fuzzy)
- "서울 여행 맛집" 처럼 다중 키워드 검색 처리
- 다양한 정렬 조건/필터 조합 (예: 별점 순, 태그 필터, 범위 필터)
- 일일 수십만 건 이상 로그/데이터 유입
- 데이터 시각화, 집계, 통계 분석도 함께 하고 싶음 (→ Kibana 연동)
- 전체 텍스트 검색 중심의 서비스 (쇼핑몰, 블로그, 관광지 검색 등)

### 🧠 Elasticsearch는 비정형 키워드를 빠르게 찾는 데 최적화

# ✏️ 어떤 차이가 있길래 검색이 빠르지?

### match: 
- 책의 index 페이지를 펼쳐 match 값이 나오는 책 번호만 집어서 찾기

# ✏️ View의 종류
## 일반 View (Standard View)
- SQL로 조인할 수 있는 가상의 테이블
- 원본 테이블의 변경이 반영됨
- 복잡한 쿼리 간소화, 보안 제어
- 매번 실행 -> 성능 부담

## 물리적 View (Materialized View)
- 조회 결과를 물리적으로 저장하는 뷰
- 주기적으로 갱신 필요
- 대량 데이터 검색/집계에 적합

# 👍결론
- 비정형 키워드를 빠르게 검색하기 위해 물리적 View를 ES에 저장하는 방식 사용
